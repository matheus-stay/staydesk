# Story 3.7: navegação do agente com divulgação progressiva

> Status: Ready for user review
> Epic: EPIC-003 Frontend StayDesk
> Lead: squad-design / Nexus
> Scope boundary: frontend-only

## Objetivo

Reduzir a carga cognitiva do menu lateral do StayDesk sem remover destinos,
alterar permissões ou mudar contratos do backend. A navegação deve aproximar o
modelo operacional do Zendesk: trabalho frequente permanece imediatamente
visível; módulos ocasionais ficam reunidos em uma entrada previsível; a área
administrativa permanece separada.

## Diagnóstico

- O menu atual apresenta até dez grupos no primeiro nível.
- Configurações pode apresentar até vinte destinos permitidos.
- Trabalho diário, CRM, conhecimento, campanhas, análise e administração têm o
  mesmo peso visual.
- Os mesmos componentes já resolvem permissões, feature flags, tipo de instalação,
  rotas com `navigationPath`, coleções dinâmicas e contadores.

## Escopo deste ciclo

- Manter visíveis: Caixa de Entrada, Conversas, Chamadas quando elegível,
  Contatos e Relatórios.
- Reunir Capitão, Empresas, Campanhas e Central de Ajuda em “Mais”.
- Manter Configurações como destino próprio, separado no fim da área rolável.
- Preservar integralmente as opções e a ordem interna de cada módulo.
- Fazer “Mais” funcionar como disclosure: abrir/recolher nunca navega para uma
  rota arbitrária.
- Melhorar semântica, foco visível e estado expandido do trigger de grupo.

## Fora de escopo

- Renomear destinos existentes ou alterar URLs.
- Mover Respostas Prontas, Macros ou qualquer recurso entre domínios.
- Alterar permissões, feature flags, paywall ou instalação elegível.
- Alterar requests, stores, APIs, Rails, banco, Sidekiq ou integrações.
- Substituir o menu por uma taxonomia nova sem tree testing com agentes e admins.

## Critérios de aceite

- [x] O primeiro nível tem no máximo sete entradas quando Chamadas está disponível.
- [x] Nenhuma rota ou opção existente deixa de ser alcançável.
- [x] `permissions`, `featureFlag`, `installationTypes` e `navigationPath` continuam
      resolvidos pela rota original.
- [x] “Mais” abre no modo expandido e recolhido sem navegar para o primeiro filho.
- [x] A rota ativa dentro de “Mais” abre e destaca o contexto correto.
- [x] Configurações permanece visível e visualmente separada ao fim do menu.
- [x] Headers de grupo são operáveis por teclado e expõem `aria-expanded`.
- [x] Estados light, dark, hover, focus, open e active são distinguíveis.
- [ ] Drawer móvel mantém labels e todos os destinos permitidos.
- [x] Nenhum arquivo de backend, Enterprise, store, rota ou API aparece no diff.
- [x] ESLint, testes frontend direcionados e build de produção passam.
- [ ] QA visual passa em 56, 200 e 320 px, desktop e mobile.

## Decisões arquiteturais

1. Aplicar divulgação progressiva sobre os mesmos objetos de navegação, sem
   duplicar contratos de rota.
2. A fonte de verdade de visibilidade continua em `provider.js` e nos metadados
   das rotas.
3. O grupo sintético usa o componente de grupo existente; nenhuma store ou
   preferência nova será criada.
4. A proposta Compass de seis domínios semânticos fica para uma próxima iteração,
   condicionada a tree testing. Este ciclo prioriza reversibilidade e baixo risco
   de sync com o upstream.
5. O estado de largura, resize, RTL e breakpoint móvel permanece intacto.
