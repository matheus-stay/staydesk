# Story 3.3: workspace do agente com UX familiar ao Zendesk

> Status: Ready for review
> Epic: EPIC-003 Frontend StayDesk
> Lead: squad-design / Nexus
> Scope boundary: frontend-only

## Objetivo

Evoluir visualmente o workspace do agente do Chatwoot para o modelo mental observado no Zendesk Support, preservando o design system StayCloud e toda a lógica funcional existente.

## Entradas

- `docs/staydesk/qa-zendesk-agent-workspace.md`
- `docs/staydesk/design/front-end-spec.md`
- `docs/staydesk/design/staydesk-tokens.md`
- `Requisitos - Sistema de Atendimento (externo).md`, usado somente como fonte de requisitos
- Componentes e estados já existentes no Chatwoot v4.17.1

## Escopo final deste ciclo

- Hierarquia visual e densidade do shell do agente.
- Separação visual clara entre navegação, lista, ticket, composer e contexto.
- Lista de conversas mais operacional e escaneável, usando somente dados já exibidos.
- Cabeçalho e superfícies do ticket alinhados ao brand guide.
- Abas de conversas no topo, persistidas por conta somente na sessão do navegador.
- Indicador visual de rascunho nas abas, reutilizando o store frontend existente.
- Painel de campos e ações do ticket à esquerda da conversa em desktop.
- Estados responsivos, foco, hover, selected e active nas superfícies alteradas.
- Nenhuma mudança em regras de negócio, contratos HTTP ou comportamento do backend.

## Fora de escopo

- Adicionar, remover, renomear ou reordenar qualquer opção existente.
- Alterar defaults ou preferências persistidas pelo Chatwoot.
- Alterar status, SLA, roteamento, macros, automações ou comportamento pós-envio.
- Criar endpoints, requests, payloads, stores, migrations ou contratos de API.
- Alterar Rails, Sidekiq, banco de dados, serviços ou integrações.
- Exibir ações que ainda não funcionam no Chatwoot.
- Usar dados mockados ou placeholders em produção.

## Critérios de aceite

- [x] Nenhum arquivo de backend aparece no diff.
- [x] Nenhum novo request HTTP, endpoint, store action ou contrato de payload é introduzido.
- [x] Preferências e defaults de layout permanecem idênticos ao Chatwoot atual.
- [x] A estrutura visual lembra o workspace diário do Zendesk sem copiar sua marca.
- [x] O layout usa tokens existentes e Tailwind, sem CSS customizado ou inline novo.
- [x] Abas e indicador de rascunho usam apenas rota, estado e dados já disponíveis no frontend.
- [x] Fechar ou alternar abas não altera tickets, mensagens ou estado no servidor.
- [x] Estados de foco, hover, active, loading e empty permanecem distinguíveis.
- [x] ESLint dos arquivos alterados passa sem erros.
- [x] Testes frontend relacionados passam.
- [x] Auditoria de acessibilidade não encontra bloqueadores nas superfícies alteradas.

## Plano e handoffs

- [x] QA do Zendesk Support documentado e Zendesk Chat legado excluído.
- [x] Corte anterior auditado e mudanças comportamentais removidas.
- [x] Compass entrega auditoria heurística e prioridades de fluxo.
- [x] Canvas entrega handoff visual alinhado aos tokens StayCloud.
- [x] Scaffold entrega mapa técnico frontend-only e implementação.
- [x] Beacon executa gate de acessibilidade.
- [x] Imperator valida o diff, os testes e a fronteira frontend/backend.

## Decisões arquiteturais

1. Replicar a composição visual e a hierarquia operacional do Zendesk, mantendo a marca e os tokens StayCloud.
2. Reutilizar dados, componentes, composables e preferências existentes.
3. Abas são um recurso de navegação exclusivamente frontend; funcionalidades operacionais continuam em stories posteriores.
4. Mudanças devem minimizar conflito com o upstream e preferir `components-next/`.
5. Nesta fase, UI/UX prioriza apresentação e navegação local; regras operacionais e integrações permanecem fora do escopo.
